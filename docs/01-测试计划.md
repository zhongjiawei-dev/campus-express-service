# 校园快递代取平台 · 测试计划

## 1. 项目背景

校园里帮同学取快递、送到宿舍楼下是常见需求。这个练习项目实现了一个简化版代取平台：学生发单并预付跑腿费，骑手接单、取件、送达，学生签收后钱从学生钱包转到骑手钱包，双方可以互评，订单每个节点写一条哈希存证。

我独立负责这个项目的测试设计与执行。服务端也是我写的，所以接口约定、状态机、异常码都以 `docs/05-接口清单.md` 为准。

## 2. 测试目标

1. 主链路能走通：下单 → 接单 → 取件 → 送达 → 签收 → 评价，每一步状态、时间、钱和信用分都对。
2. 异常分支不穿透：重复操作、越权操作、超时订单、余额不足、参数越界都要被拦住。
3. 数据能对上：接口返回的订单、钱包余额、流水、信用分，和数据库里的多表关联结果一致。
4. 存证能验伪：订单关键字段被改过以后，哈希校验要能发现。
5. 回归能重复跑：一条命令起服务、跑全量用例，CI 上也能跑。

## 3. 测试范围

### 3.1 包含

| 模块 | 接口数 | 关注点 |
| --- | --- | --- |
| 账号与鉴权 | 5 | 注册参数、登录、Token 失效/过期/畸形、手机号脱敏 |
| 订单 | 8 | 下单参数边界、余额校验、列表筛选分页、详情、取消、越权 |
| 状态流转 | 5 | 接单、取件、送达、签收、评价的状态前置与角色限制 |
| 钱包与信用 | 4 | 余额、充值、流水、信用分变动 |
| 存证 | 2 | 时间线、哈希链校验、篡改检测 |
| 管理端 | 2 | 订单列表、统计 |

合计 22 个接口（含健康检查）。

### 3.2 不包含

- 真实支付渠道、短信验证码、消息推送
- 前端页面兼容性和样式
- 性能压测、安全渗透
- 多机部署和容灾

这些不在这次练习的范围内，硬做也做不深。

## 4. 测试策略

### 4.1 接口测试

用 pytest + requests，按业务模块拆文件。每个用例自己造数据，不依赖上一条用例留下的状态。`conftest.py` 里做了几件事：

- session 级 fixture 在空闲端口拉起被测服务，轮询 `/api/health` 直到可用
- 每个用例前清空订单、流水、存证、信用分记录，把种子账号的钱包和信用分复位
- 封装 `Client`，统一带 `Authorization: Bearer <token>`
- 提供学生、骑手 A、骑手 B、管理员四种身份的 token
- 提供待接单、已接单、配送中、已送达、已签收五种订单 fixture

### 4.2 参数与异常

金额、超时时间、文本长度这些边界单独列。等价类加边界值，能参数化的就参数化。异常分支重点看三件事：HTTP 状态码、业务 code、message 是否对得上。

### 4.3 数据驱动

下单参数校验放在 `data/order_cases.yaml`，一条 YAML 一个场景，测试函数只负责发请求和断言。加场景改 YAML 就行，不用动代码。

### 4.4 数据库核对

接口说成功不算数，钱和状态要落库。用 PyMySQL 直连，查这几组关系：

- `orders.fee_cents` 和创建时传的金额是否一致
- 签收后 `users.wallet_cents` 是否等于初始值减跑腿费
- `flows` 里付款和收入两条流水的金额、关联单号是否对得上
- `credit_logs` 的变动值和 `users.credit_score` 是否同步
- `chain_records` 的条数、`prev_hash` 串联关系

### 4.5 存证校验

每个节点把订单号、事件、标题、状态拼起来算 SHA-256，`prev_hash` 指向上一条的 `record_hash`。测试里直接改库：

- 改 `orders.status`，期望校验失败
- 改 `orders.title`，期望校验失败
- 改 `orders.fee_cents`，看哈希有没有覆盖金额

### 4.6 手工接口验证

Postman 集合按文件夹组织，先登录拿 token，再按主链路顺序跑。集合里的测试脚本会断言状态码和关键字段，`order_id` 自动带到后续请求。

## 7. 准入与准出

**准入**

- 服务能起来，`/api/health` 返回 `up`
- 22 个接口的路径、参数、返回结构清楚
- 种子数据可用

**准出**

- 全量用例执行完毕，没有 error
- 通过率不低于 95%，未通过的都是已登记缺陷且能复现
- P0/P1 缺陷有明确复现步骤
- 执行报告里的数字和实际跑出来的一致

## 8. 风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 用例之间互相污染数据 | 结果不稳定 | 每个用例前清库并复位种子数据 |
| 服务端起得慢 | 首批用例连接失败 | fixture 轮询 health，最多等 20 秒 |
| 依赖本机数据库 | 换机器跑不起来 | 连接参数走环境变量，CI 用 service 容器 |
| 存证只比对部分字段 | 篡改漏检 | 专门写改金额的用例，把问题暴露出来 |
