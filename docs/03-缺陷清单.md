# 校园快递代取平台 · 缺陷清单

测试时间：2026-11-18  
测试环境：Ubuntu 22.04 / Python 3.12 / MariaDB 10.6  
测试范围：22 个接口、113 条自动化用例、27 个 Postman 请求

一共记录 5 个服务端问题。都实际复现过，当前版本没改，用例里用 `xfail` 标着。这个仓库是测试练习，留着这些缺陷是为了让「发现问题 → 复现 → 记录」这条链有据可查；改掉服务端，对应的 xfail 就失去意义了。

## CX-01 签收后双方信用分都没有增加

**级别** P1  
**模块** 签收 / 信用分  
**发现用例** `test_lifecycle.py::test_credit_after_sign`

**前置条件**

- 学生 13800000001 发单，跑腿费 8.50
- 骑手 13800000002 接单、取件、送达
- 学生签收

**复现步骤**

1. 三个角色登录，拿 token
2. 学生调 `POST /api/orders` 建单
3. 骑手依次调 `/take`、`/pickup`、`/deliver`
4. 学生调 `/sign`
5. 学生和骑手分别调 `GET /api/credit`

**预期** 双方信用分从 100 变成 102（规则写的是签收后双方 +2）

**实际** 双方都还是 100，`credit_logs` 里没有签收相关的记录

**影响** 信用分规则形同虚设，按时签收的用户得不到正向激励。

**初步定位** `sign_order()` 只更新订单状态和钱包，没有写信用分变动，也没有写 `credit_logs`。评价接口里有加减分逻辑，签收接口里没有。

**建议** 在签收事务里补两条信用分变动（下单人 +2、骑手 +2），并写对应 `credit_logs`；变动值和订单号一起落库，方便核对。

## CX-02 已签收订单可以重复签收，重复扣款

**级别** P0  
**模块** 签收 / 钱包  
**发现用例** `test_lifecycle.py::test_sign_twice_should_reject`

**前置条件**

- 一笔已送达订单，学生钱包 300.00，骑手钱包 50.00，跑腿费 8.50
- 学生已经签收过一次

**复现步骤**

1. 学生第一次调 `POST /api/orders/{id}/sign`，返回 200
2. 学生再调一次同样的接口
3. 查双方钱包和 `flows`

**预期** 第二次返回 409 / 40902「当前状态不能签收」，钱包不再变化

**实际** 第二次仍返回 200，状态还是 signed；学生钱包 300 → 283.00，骑手 50 → 67.00；`flows` 里出现两条 `order_pay`、两条 `order_income`，同一单号

**影响** 重复点击、网络重试、脚本误调用都会造成重复扣款，属于资金问题。

**初步定位** `sign_order()` 的状态判断把 `signed` 也放进了允许集合，而且没有幂等键或「已签收」二次校验。

**建议** 只允许 `delivered` 签收；签收前用订单号做一次幂等检查；钱包变动和订单状态更新放在同一个事务里，失败整体回滚。

## CX-03 超过接单时限的订单仍然可以被接单

**级别** P1  
**模块** 接单 / 超时  
**发现用例** `test_timeout.py::test_take_expired_should_reject`

**前置条件**

- 学生建一笔 `timeout_minutes=10` 的订单
- 把 `orders.created_at` 改到 20 分钟前，使订单过期

**复现步骤**

1. 学生建单
2. 直接改库，把创建时间往前拨 20 分钟
3. 骑手调 `POST /api/orders/{id}/take`

**预期** 409 / 40904「订单已超时，不能接单」

**实际** 200，接单成功，`status=taken`

**影响** 骑手可以接已经过期的单，学生可能已经取消或另找人了，容易产生纠纷。

**初步定位** `take_order()` 只判断 `status == pending`，没有调 `is_expired()`；详情接口和列表接口都算了 `expired` 字段，接单接口没用上。

**建议** 接单前先判断是否过期；过期订单统一置为 `cancelled` 或新状态 `expired`，并在列表里过滤掉。

## CX-04 存证哈希没有覆盖金额，改金额查不出来

**级别** P2  
**模块** 存证  
**发现用例** `test_chain.py::test_verify_after_fee_tamper`

**前置条件**

- 一笔已签收订单，存证 5 条
- 正常校验返回 `valid=true`

**复现步骤**

1. 调 `GET /api/orders/{id}/verify`，确认 valid=true
2. 改库：`UPDATE orders SET fee_cents=1 WHERE id=?`
3. 再调一次 verify

**预期** valid=false，`broken_at` 指向被改的那条

**实际** valid=true，checked=5

**影响** 订单金额被改以后，存证仍然显示「未被篡改」，存证的公信力打折。

**初步定位** 哈希原文是 `prev_hash|order_id|event|title|status`，payload 里虽然带了 `fee`，但 `fee` 没参与 `record_hash` 计算；`verify_chain()` 也只重新比对了 title 和 status。

**建议** 把 fee、pickup、dropoff、courier_id 这些关键字段纳入哈希原文；校验时按同样的字段顺序重算，不要只比两个字段。

## CX-05 同一订单可以重复评价，信用分重复加减

**级别** P2  
**模块** 评价 / 信用分  
**发现用例** `test_lifecycle.py::test_review_twice_should_reject`

**前置条件**

- 一笔已签收订单
- 学生已提交 5 星评价

**复现步骤**

1. 学生调 `POST /api/orders/{id}/review`，rating=5
2. 同一个学生再调一次，rating=1
3. 查 `GET /api/credit`

**预期** 第二次返回 409 / 40902「该订单已评价」

**实际** 第二次返回 200，`review_rating` 被改成 1；`credit_logs` 出现两条记录（+1 和 -1），信用分最后还是 100

**影响** 评价结果可以被反复覆盖，信用分变动记录失真；如果只刷 5 星，可以把分刷高。

**初步定位** `review_order()` 没有检查 `review_rating IS NULL`，每次调用都直接更新并写信用分。

**建议** 评价前判断是否已评价；`orders.review_rating` 加非空校验；信用分变动和评价更新放同一事务。
