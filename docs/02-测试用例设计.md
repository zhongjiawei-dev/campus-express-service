# 校园快递代取平台 · 用例设计

## 1. 设计思路

先按角色分：下单的学生、接单的骑手、管数据的管理员。再按状态分：`pending → taken → delivering → delivered → signed`，外加 `cancelled`。每个状态问三个问题：

1. 谁有权限做这个操作？
2. 什么状态下能做？
3. 做完以后钱、信用分、存证分别变成什么？

异常用例主要从这四个方向来：重复做、换人做、提前做、参数不对。

## 4. 数据设计

### 4.1 账号

固定四个种子账号，测试前复位钱包和信用分。注册用例每次生成一个随机手机号，避免唯一键冲突。

### 4.2 订单金额

- 正常值：8.50（用例里最常用，方便算钱）
- 下边界：1.00
- 上边界：500.00（先把钱包充到 600 再下单）
- 越界：0.99、500.01、-1.00
- 格式错误：三位小数、字母、null

### 4.3 超时时间

- 正常：30 分钟
- 下边界：10 分钟
- 上边界：180 分钟（只验证接口接受，不真等）
- 越界：9、181、0

超时场景不真等 10 分钟，直接改数据库里的 `created_at`，把订单「变老」。这样用例跑得快，也不依赖 sleep。

### 4.4 YAML 驱动

`data/order_cases.yaml` 有 11 条，字段是 `name`、`fee`、`timeout`、`patch`、`status`、`code`。`patch` 用来覆盖 title、pickup 这类字段，测试函数只做一件事：拼请求、比对状态码和 code。

## 5. 预期失败的 5 条

这 5 条用 `@pytest.mark.xfail` 标了，不是跳过，是明确告诉 pytest「这条现在会失败，原因已知」：

| 用例 | 缺陷 | 实际表现 |
| --- | --- | --- |
| test_sign_twice_should_reject | CX-02 | 第二次签收返回 200，再扣一次钱 |
| test_credit_after_sign | CX-01 | 签收后双方信用分仍是 100 |
| test_review_twice_should_reject | CX-05 | 第二次评价返回 200，信用分重复加减 |
| test_take_expired_should_reject | CX-03 | 超时单仍能接 |
| test_verify_after_fee_tamper | CX-04 | 改了金额，存证仍显示 valid |

`xfail` 和 `skip` 的区别在于：xfail 的用例是真的执行了的，只是结果不符合预期。执行报告里 5 条 xfailed 就是这么来的。

## 6. 没覆盖到的

- 并发抢单只用两个骑手顺序调用模拟，没有真并发压测
- Token 过期只造了数据库记录，没有等 2 小时
- 存证只测了 SHA-256 链，没有接真实区块链
- 管理端只有查询，没有权限细粒度测试

这些在练习项目里性价比不高，先记下来。
